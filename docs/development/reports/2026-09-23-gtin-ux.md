# UX Experiment — GTIN (120 inputs, public API only)

**Date:** 2026-09-23
**Method:** black-box, as a library user. 120 inputs (111 `assert` / 9 `explore` = 7.5% explore, seeded RNG `20260923`), run through `paxman.canonicalize()` under 6 contracts (720 matrix calls, plus ~23 post-hoc diagnostic probes through the same API): `default` / `include_verified=True` / `suppress_common_words=True` / `year=2018` / `output_format="native"` / `output_format="hri"` (error path). Expectations were recorded per input **at generation time** from spec tables only — the guide statuses table (`docs/user/capabilities/gtin.md`), the research inventory (§2 forms, §8 statuses, §9 resolution map), and the GenSpecs Mod-10 formula — never from the implementation; implementation code was consulted only post-hoc to diagnose mismatches and explain observations. Non-default expectations are equivalence-class transforms of the default row (verified ≡ default; suppress ≡ default; `year=2018`: SUCCESS→INVALID else unchanged; native: status unchanged, SUCCESS value = the spelled run; hri: `ContractError` naming the legal set). **This run is a pre-merge acceptance sweep**: it executed against the uncommitted GTIN working tree (the capability has not landed on `dev`). No source, test, or config was modified; disposable scripts and data (`/tmp/opencode/gtin_ux_*`) were deleted after this report was written — the sweep's repo diff is this file only.

SUCCESS 55→53 and MME 3→5 account for each other exactly.

## Findings

**1. [BUG — implementation] `output_format="native"` breaks same-entity duplicate coalescing: `MultipleMentionsError` instead of `SUCCESS`.** *(Resolved in-branch, 2026-09-23 — fix landed test-first before the PR; no issue needed.)*
Vectors: `"00614141999996 and 614141999996"` and `"12345670 and 00000012345670"` → default/verified/suppress all `SUCCESS` (one coalesced value, per guide line 79 and row 100), `native` raises `MultipleMentionsError: Input contained 2 distinct mentions resolving to 2 distinct canonical values (['00614141999996', '614141999996'])`. Control: the identical-spelling pair `"96385074 96385074"` coalesces to `SUCCESS` under `native` too — localizing the defect to format-resolved value comparison, not multi-mention handling per se. Mechanism (confirmed against `paxman/engine/orchestrator.py`): `_collect_candidates` applies the presentation seam `capability.format_value(...)` while building candidates (orchestrator.py:595), so `Candidate.value` is already format-resolved when `_enforce_single_value_invariant` (orchestrator.py:152, :621) and `_dedup_candidates` (orchestrator.py:154) make *identity* decisions. Under `native`, GTIN's seam renders per the notation's `native_length` facet, so the two spellings of one entity format to two different strings; the invariant then sees two distinct "canonical values" across two separate mentions and raises. Under `default` both spellings render `00614141999996`, one distinct value, coalesce. This violates three stated invariants at once: the capability seam's own contract (`output_format` "Never affects candidate identity or provenance"), guide line 79 (coalesce claim, unqualified by contract), and ADR-0011 (native is an *encoding* of one entity — entity-relative injectivity, status must not change with format). It is latent engine-wide: any capability with a spelling-dependent format hits it; `native` is the first shipped one. **Fix direction:** identity decisions (single-value invariant, dedup key) must run on the pre-format canonical value; `format_value` moves to result assembly (`ExecutionResult.candidates` emission + `canonicalized_value`). Blast radius to weigh: shared engine change, so every offered format's entity-constant assumption needs a parity check — this is a plan deviation (the plan excluded engine changes) and is the merge-blocking decision for this branch. Verdict: implementation bug, status/value contract broken under an offered format; not triggered by any released capability (GTIN has not landed).

**Resolution (in-branch, same day):** identity decisions — the single-value invariant, the dedup key, status determination, and the single-value span condition — now read canonical, pre-format values; `format_value()` runs exactly once at result assembly (`_format_candidates`), rebuilding each surviving candidate with the same rule names, provenance, and span and rendering its value with the source recognition's notation. Regression tests cover both vectors (SUCCESS, first mention's spelling rendered, span pinned), the two controls (identical-spelling coalesce; distinct-entity MME preserved), and cross-format status parity. The same defect class surfaced two latent engine twins, fixed alongside: the Phone `rfc3966` extension pair (raised MME under `rfc3966` while the default contract coalesced — status varied by format) and the format-seam test contract (which pinned format-before-identity as intended behavior). Living docs describing the old ordering were updated (`ARCHITECTURE.md`, `HOW_TO_ADD_NEW_CAPABILITY.md`, ADR-0010 code pointer); dated research reports/plans were left as historical record. Full gate re-run green.

**2. [DOC — guide row overstates] Two distinct GTINs under `year=2018` → `INVALID`, not `MultipleMentionsError`.**
Vectors: `"614141999996 / 5012345670003"`, `"96385074 and 5012345670003"`, `"UPCs: 614141999996, 96385074"` → default `MME` (correct), `year=2018` → `INVALID` (expected `MME` per guide row 118's "any" contract cell). Mechanism: `year=2018` drops all three rules (2026/2026/2019), so no candidate ever qualifies; `_enforce_single_value_invariant` returns on empty input and never evaluates ambiguity — recognition with zero qualifying rules falls to `INVALID` (guide row 109 documents exactly this for the single-mention case: `year=2018` → `INVALID`, "every rule is newer, dropped"). MME is defined over distinct *resolved* values; with no rules there are none to compare. The behavior is principled and consistent; the guide cell "any" overstates. Verdict: spec correction — qualify row 118's contract cell (e.g. "any rule-active contract; a filter that drops every rule yields `INVALID` first, per row 109"). Follow-up: written reason no issue — the guide ships for the first time with this branch (untracked on `dev`), so the correction rides the GTIN PR; an issue would describe a doc that does not exist on `dev` yet. *(Correction applied in-branch: row 118's contract cell now reads "any rule-active contract" with the rule-drop note.)*

**3. [SWEEP EXPECTATION ERROR — product correct] `5 0123 45670 03` expected `SUCCESS`, observed `INVALID` under default/verified/suppress/native.**
Root cause is at generation time, not in the product. The expectation was transcribed from research §2.2#3's illustration *"`0 50123 45670 03`-style"* — but that string collapses (separators stripped) to `0501234567003`, a 13-digit run whose Mod-10 expected check is 5 vs actual 3 → `INVALID` (reproduced by probe); my generated variant collapses to `501234567003`, expected 5 vs actual 3 → `INVALID` (hand-checked against the GenSpecs formula). The genuine grouping of the guide's EAN-13 `5012345670003` is `5 01234 56700 03`, which probes `SUCCESS → 05012345670003` — so grouped recognition itself works. `INVALID` on a failed check digit is exactly the guide's line 7 rule ("a bad check digit … is `INVALID`, never a guess"). Verdict: expectation derived from a research illustration that is not itself a check-valid grouping; no product action. The research specimen typo is noted in passing — follow-up: written reason no issue, `docs/development/` is explicitly non-shipping and drift-tolerant per its own AGENTS.md.

**4. [DOC — guide row overstates] "Coupon / extended-code shapes → `MISSING` (REJECT in v1)" — there is no coupon guard; the 13-digit `020`/`981` families validate normally.**
Vectors (post-hoc probes, since the explore row was expectation-free): `0201234567890` → `INVALID` (claimed 13-run, check fails — the sweep explore row); `0201234567899` (check-valid) → `SUCCESS → 00201234567899`; `9810000000006` (check-valid) → `SUCCESS → 09810000000006` (prefix table allocates 981–984, "GS1 coupons (common currency)"); `036000291452+12345` → `SUCCESS → 00036000291452` (add-on digits dropped, base UPC-A canonicalized); `036000291452-12345` → `MISSING` (the `(?!\…-\d)` trailing guard, not coupon detection); `CPN0201234567890` → `MISSING` (letter glue, generic boundary rule). Mechanism: a 13-digit `020–029` run is shape-identical to an EAN-13 — nothing in the grammar can distinguish it, and the research deliberately left the disposition an Open Decision (§13#11: "confirm in GenSpecs §§1–2 before ruling", evidence marked *unverified*); the plan shipped no guard, consistent with never inventing rules from unverified evidence. Every `MISSING` outcome above comes from generic glue/hyphen guards. Verdict: spec correction — guide row 22 overstates a rejection that was never implemented; the cell should describe actual behavior (check/prefix decide as for any EAN-13; glued and hyphen-add-on forms `MISSING` via generic guards) or the guard must be implemented once GenSpecs confirms. Follow-up: written reason no issue — the underlying question is already tracked as research Open Decision §13#11 (primary source blocked by gs1.org WAF, research §15), and the guide row ships first with this branch, so the correction rides the GTIN PR. *(Correction applied in-branch: row 22's cell now describes actual behavior — `020`/`981` families validate like any number, glued `+add-on` reads its core, hyphen add-on and `CPN…` forms `MISSING` via generic guards.)*

## Verdict

Refusal design, value correctness, flag semantics, year filtering, and the contract-error UX all read as intended: no wrong value, no wrong `SUCCESS`, no surprise exception in 720 calls. Three of four findings are documentation/sweep artifacts; Finding 1 (native coalesce → MME) was a real defect in the presentation-before-identity layering and is **resolved in-branch** — identity now reads canonical values, formatting applies at result assembly — together with the two guide corrections, all riding this branch's PR.
